Content-pipeline-kit plugin packaging: bootstrap configuration, public API surface contract, one-unit worker agent, consumer contract checker, and parallel wave workflow.

This is the packaging and contract layer of the content-pipeline-kit plugin. The library that does the work, and the skills that teach the agents, each live one level down with their own pages; what sits in this root is what wraps and ships them. It declares the plugin's version and its single dependency, commits to a public API surface, and provides the two ways a run is actually driven. The plugin is the seam between making one LLM call, a lower layer's job, and running many of them, so every piece here is a run-level concern: provisioning the environment, holding the public surface steady, and executing units.

Where to start

Start with plugins/content-pipeline-kit/README.md for the shape of the plugin and where each concern lives. Open plugins/content-pipeline-kit/bootstrap.json when you need to know what the plugin pulls in and the version floor it requires.

Provisioning and identity

  • plugins/content-pipeline-kit/bootstrap.json -- the bootstrap configuration: what the plugin pulls in and requires (the bootstrap floor, the auto-installed llm-scripting-kit dependency with its minimum version, the shared library published from the library directory) and the project-config fields the plugin collects on first run.
  • plugins/content-pipeline-kit/.claude-plugin/plugin.json -- the plugin manifest: name, version, the bootstrap dependency, and keywords. Bump it together with the package definition, because both must stay in lockstep with the library's version constant.
  • plugins/content-pipeline-kit/pyproject.toml -- the Python package definition: the version, the dependencies (pyyaml, ruamel.yaml, openai), and the package discovery rooted at the library directory.

The public API surface and its checker

  • plugins/content-pipeline-kit/contract/public-surface.json -- the machine-readable list of every public, deprecated, and removed name, each with a removal version and replacement text. Open it to see why the checker flagged a name.
  • plugins/content-pipeline-kit/scripts/check_consumer_contract.py -- a static AST scanner that reports which content_pipeline names a consumer uses are deprecated or removed, and exits 1 when a removed name appears. It reads the surface contract to resolve each finding, and it also fails on deprecated names when run in strict mode.

The run drivers

  • plugins/content-pipeline-kit/agents/pipeline-worker.md -- the one-unit background worker agent. It claims exactly one unit, produces an answer, and submits it, then exits; a consumer selects it when launching a background session through the dispatcher.
  • plugins/content-pipeline-kit/workflows/run-ready-wave.js -- the parallel workflow script. It runs a prepared wave through N agent lanes, each agent claiming, reading, answering, and submitting its own unit through the protocol seam; it performs no persistence of its own.

Overview and agent guidance

  • plugins/content-pipeline-kit/README.md -- the human-facing overview: the seam between one call and a run, cost and budget, structured output, and how to drive a run.
  • plugins/content-pipeline-kit/CLAUDE.md -- the agent-facing rules: the one-way dependency split, backend selection, the adaptive gate, and the parallel graph, deadline, and failure-cache behavior. Open it to change how a consumer or worker behaves.
